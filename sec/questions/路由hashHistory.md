# hash 和 history 路由的区别

在前端路由中，`hash` 模式和 `history` 模式是实现单页应用（SPA）路由跳转的两种主要方式，核心区别在于 URL 表现形式、底层原理和使用限制，以下是详细对比：


## 1. URL 表现形式

- **hash 模式**  
  URL 中包含 `#` 符号，`#` 后面的部分为哈希值（如 `http://example.com/#/home`）。  
  `#` 及其后面的内容不会被发送到服务器，仅用于前端路由识别。

- **history 模式**  
  URL 与传统 URL 一致，不包含 `#`（如 `http://example.com/home`），看起来更美观、接近真实的网页路径。


## 2. 底层实现原理

- **hash 模式**  
  基于浏览器的 `window.location.hash` 属性和 `hashchange` 事件：  
  - 当哈希值（`#` 后面的内容）变化时，浏览器不会重新加载页面，但会触发 `hashchange` 事件。  
  - 前端框架监听 `hashchange` 事件，根据新的哈希值渲染对应的组件。

- **history 模式**  
  基于 HTML5 新增的 `History API`（`pushState()`、`replaceState()`）：  
  - 通过 `history.pushState()` 可以在不刷新页面的情况下修改 URL，并将新 URL 加入浏览器历史记录。  
  - 通过 `history.replaceState()` 可以修改当前 URL 但不新增历史记录。  
  - 监听 `popstate` 事件（用户点击前进/后退按钮时触发），根据当前 URL 渲染对应的组件。


## 3. 核心区别对比

| 对比项               | hash 模式                          | history 模式                          |
|----------------------|-----------------------------------|--------------------------------------|
| URL 美观性           | 含 `#`，不够美观                  | 无 `#`，更接近传统 URL               |
| 兼容性               | 支持所有浏览器（包括 IE8 及以下） | 依赖 HTML5 History API，仅支持 IE10+ |
| 服务器依赖           | 无（刷新页面不会 404）            | 有（需服务器配置，否则刷新 404）      |
| 可修改的 URL 范围    | 仅 `#` 后面的部分                 | 可以修改整个 URL（同域内）            |
| 历史记录操作         | 仅能通过 `hash` 变化新增记录      | 可通过 `pushState` 自由新增/替换记录  |
| 传递参数的直观性     | 哈希中携带参数，不够直观（如 `#/user?id=1`） | 可在路径中传递参数（如 `/user/1`）   |


## 4. 关键限制与问题

- **hash 模式的限制**  
  - URL 中必须包含 `#`，影响美观和 SEO（虽然现代搜索引擎已能识别哈希，但仍有局限性）。  
  - 哈希值只能包含 ASCII 字符，特殊字符需要编码。  

- **history 模式的限制**  
  - **服务器配置要求**：当用户直接访问 `http://example.com/home` 等子路径时，服务器会尝试寻找对应的物理文件，若未找到会返回 404。因此需要服务器配置“所有请求都指向 SPA 的入口文件（如 `index.html`）”，让前端路由接管处理。  
    示例 Nginx 配置：  
    ```nginx
    location / {
      try_files $uri $uri/ /index.html; # 所有请求转发到 index.html
    }
