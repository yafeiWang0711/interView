### 5. vite的按需加载怎么实现的？
    Vite 的按需加载（代码分割）本质上是基于 ES 模块的动态导入（import() 语法）实现的，结合 Rollup 的打包能力，在开发和生产环境中通过不同机制确保高效的按需加载体验。
    核心原理：ES 动态导入（import()）
    开发环境：原生 ESM 按需加载
    Vite 在开发环境中基于原生 ESM 运行，不打包全部代码，而是通过以下方式实现按需加载：
    请求拦截与转换：
    当浏览器请求某个模块时，Vite 服务器会即时编译该模块（如处理 TypeScript、JSX 等），并返回转换后的 ESM 代码。
    动态导入的即时处理：
    对于 import() 语法，Vite 会直接返回一个指向该模块的 ESM 导入路径，浏览器遇到时会自动发起新的请求加载该模块，实现真正的 “按需加载”（无需预打包）。
    例如，import('./HeavyComponent') 会被转换为浏览器可识别的 ESM 动态导入，触发对 HeavyComponent 模块的单独请求。
    无打包开销：
    开发环境中无需提前拆分代码块，浏览器按需请求模块，启动速度极快，且模块缓存机制（基于 HTTP 缓存）进一步提升效率。
    生产环境：Rollup 打包分割
    生产环境中，Vite 使用 Rollup 进行打包，通过分析代码中的 import() 语法，自动拆分代码块，实现按需加载：
    代码分割（Code Splitting）：
    Rollup 会将 import() 导入的模块识别为 “分割点”，将其打包为独立的 chunk 文件（如 HeavyComponent.xxx.js）。
    自动命名与路径处理：
    生成的 chunk 文件名会包含哈希（如 HeavyComponent.8f3b.js），用于长期缓存；同时自动处理模块间的依赖关系，确保加载顺序正确。
    加载逻辑注入：
    Rollup 会为动态导入注入加载逻辑，确保在运行时通过 <script> 标签动态加载对应的 chunk，并执行回调。

### 6. webpack也可以热更新，增量patch怎么实现的？
    webpack热更新是通过webpack-dev-server实现的，它会在代码发生改变时，自动打包代码，并且将打包后的代码发送给浏览器，浏览器收到代码后，会用新的代码替换旧的代码，实现热更新。
    增量patch：webpack热更新是增量更新，只更新发生改变的代码，而不是全部更新，所以更新速度很快。
    全量patch：webpack热更新是全量更新，每次更新都要打包全部代码，所以更新速度很慢。

    Webpack 的热模块替换（Hot Module Replacement，HMR）核心是通过增量更新（Incremental Patch） 实现的 —— 即只更新变化的模块，而非全量重新加载整个应用。其增量 patch 的生成和应用过程涉及编译时的模块差异计算、运行时的模块替换逻辑，
    以下是增量 patch 的关键步骤：
    1. 监听变化
        监听文件修改，通过模块哈希值识别变化的模块及依赖它的相关模块。
    2. 生成增量补丁
        仅重新编译变化的模块及其依赖，打包为小体积的增量补丁（.hot-update.js）。
    3. 推送与下载
        通过 WebSocket 通知客户端有更新，客户端下载增量补丁。
    4. 动态替换
        客户端运行时用补丁中的新模块替换旧模块，执行自定义更新逻辑（如重新渲染组件），无需刷新页面。
    核心逻辑：只处理变化的部分，通过模块缓存和依赖追踪实现 “局部更新”。

### 10. 项目中登录流程如何实现的，模板适配什么意思？
    登录流程：
        1. 登录页：用户输入用户名和密码，点击登录按钮。
        2. 登录验证：前端将用户名和密码发送给后端，后端验证用户名和密码是否正确。
        3. 登录成功：后端返回登录成功的消息，前端收到消息后，将登录状态设置为已登录，并且将登录信息存储在本地（如 localStorage 或 sessionStorage）。
        4. 登录失败：后端返回登录失败的消息，前端收到消息后，提示用户登录失败。
    模板适配：
        1. 响应式布局：使用 CSS 媒体查询和 flexbox/grid 布局，使页面在不同屏幕尺寸下有良好的显示效果。
        2. 图片适配：使用 srcset 和 sizes 属性，根据不同屏幕尺寸加载不同分辨率的图片。
        3. 字体适配：使用 @font-face 定义不同字体文件，根据屏幕尺寸加载不同字体。
        4. 元素适配：使用 transform、scale、translate 等属性，根据屏幕尺寸调整元素大小和位置。

### 11. 这个token存在哪里？存在Cookie和LocalStorage里有什么不同？代码如何修改?
    token存在Cookie和LocalStorage里有什么不同？
        1. Cookie：
            1. 存储位置：Cookie 存储在浏览器的内存中，每次请求都会发送给服务器。
            2. 大小限制：每个 Cookie 的大小不能超过 4KB。
            3. 安全性：Cookie 可以设置为 HttpOnly，防止 XSS 攻击。
        2. LocalStorage：
            1. 存储位置：LocalStorage 存储在浏览器的本地存储中，不会发送给服务器。
            2. 大小限制：每个 LocalStorage 的大小不能超过 5MB。
            3. 安全性：LocalStorage 不可以设置为 HttpOnly，不能防止 XSS 攻击。
    代码如何修改？
        1. 登录成功后，将 token 存储在 LocalStorage 中。

### 13. 前端常见的网络攻击有了解吗？
    前端常见的网络攻击有：
        1. XSS 攻击：跨站脚本攻击，攻击者通过在网页中注入恶意脚本，窃取用户信息或进行其他攻击。
            解决方法：
                1. 输入校验：对用户输入进行校验，过滤掉恶意脚本。
                2. 输出编码：对输出的内容进行编码，防止浏览器将其解析为脚本。
                3. 内容安全策略（CSP）：设置 Content-Security-Policy 头，限制加载的资源类型和来源。
                4. 防止点击劫持：设置 X-Frame-Options 头，防止网页被嵌入到 iframe 中。
        2. CSRF 攻击：跨站请求伪造攻击，攻击者通过伪造用户请求，执行非预期的操作。
            解决方法：
                1. 验证码：在表单中添加验证码，防止 CSRF 攻击。
                2. 令牌：在表单中添加令牌，防止 CSRF 攻击。
                3. 同源策略：浏览器会限制从一个源加载的文档或脚本与从另一个源加载的资源进行交互，防止 CSRF 攻击。
                4. 防止点击劫持：设置 X-Frame-Options 头，防止网页被嵌入到 iframe 中。
        3. 点击劫持：攻击者通过在网页中添加透明的 iframe 层，诱使用户点击错误的链接，执行非预期的操作。
            解决方法：
                1. 设置 X-Frame-Options 头，防止网页被嵌入到 iframe 中。
        4. 中间人攻击：攻击者截获用户和服务器之间的通信，窃取用户信息或篡改通信内容。
